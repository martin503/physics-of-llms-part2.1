# iGSM data generation: ordering, difficulty, and why we shuffle

This documents *how* the packed training data is laid out on disk, because the layout is
**not i.i.d.** and that directly drives the training-time shuffle configuration. Source:
[`src/data/igsm.py`](../src/data/igsm.py) and the iGSM submodule
[`iGSM/data_gen/prototype/id_gen.py`](../iGSM/data_gen/prototype/id_gen.py).

## Takeaways

- The data is **block-structured by difficulty**, not i.i.d. and not curriculum.
- **Shuffling is strongly recommended**
- The safe buffer size scales with `batch_size / workers`. Prefer **many workers** at generation
  time — it both parallelizes generation and yields fine-grained difficulty blocks that a small
  shuffle buffer can mix.

## Pipeline summary

[`generate_to_dir`](../src/data/igsm.py) produces `num_problems` problems in **batches**. Batches are processed
**sequentially**; one batch becomes exactly one parquet shard (`batch_NNNNNN.parquet`). Each
batch is split **across all workers**, packed by concatenation into
fixed 768-token windows¹, and written atomically. Shards are later read back in filename order.

¹_[`DEFAULT_CONTEXT_LENGTH`](../src/data/igsm.py)` = 768` is what actually determines the window size._

## Batches are split across workers (not one batch per worker)

Per batch, [`_generate_batch_in_pool`](../src/data/igsm.py) calls
`_worker_counts(batch_size, workers)`, which divides *that batch's* problems evenly over **all**
workers and submits one [`_generate_chunk`](../src/data/igsm.py) task per worker:

```python
counts  = _worker_counts(num_problems, workers)          # batch_size split across workers
futures = [pool.submit(_generate_chunk, c, base_seed + i, ...) for i, c in enumerate(counts)]
streams = [p for f in futures for p in f.result()]        # concatenated in worker order
```

So a batch/shard is `workers` contiguous **chunks** laid end to end: chunk 0 (worker 0), then
chunk 1 (worker 1), … Each chunk holds `batch_size / workers` problems.

## Each worker chunk is a single difficulty

This is the key fact that requires shuffling. Difficulty in iGSM-med varies almost entirely along one axis:
the **operation count** (`op`). A worker chunk is generated by **one** `IdGen` instance
([`_generate_chunk`](../src/data/igsm.py) creates it once and reuses it for the whole chunk),
and that instance fixes its target op count **once, at construction**:

```python
self.op_ = self.gen_sol_op(op_style)   # 'light' -> min(rand[1..max_op], rand[1..max_op]); FIXED
```

Every `gen_prob` call then **rejection-samples** until it finds a problem matching that fixed
target ([`id_gen.py:241`](../iGSM/data_gen/prototype/id_gen.py)):

```python
if self.problem.n_op != self.op_ or self.problem.to_hash() not in ava_hash:
    continue        # keep trying until n_op == self.op_
```

Therefore **all ~`batch_size/workers` problems in a chunk have the identical op count.** The
other med knobs are fixed too (`perm_level=5` → "hard", `detail_level=0` → one verbosity), so op
count is the only difficulty that varies — and it varies *between* chunks, not within them.

### Difficulty distribution

Each chunk's `op_` is `min` of two independent draws from `uniform[1, max_op]` (the `'light'`
style), which skews toward lower op counts. Across the many chunks (`workers × num_batches`
independent draws), the dataset's op-count histogram follows that `min`-of-two distribution.
Chunk-to-chunk op order is **random**, not monotonic — so this is **not** a curriculum.

## Resulting on-disk structure

```
shard b (= batch b):
  [ worker 0: N problems, all op = k_{b,0} ]
  [ worker 1: N problems, all op = k_{b,1} ]
  ...
  [ worker W-1: N problems, all op = k_{b,W-1} ]     # N = batch_size / workers; k_* random
concatenated, then chunked into 768-token windows (partial tail dropped per batch)
```

- Contiguous **runs of same-difficulty windows**, run length ≈ one chunk.
- Difficulty resets randomly at each chunk boundary.
- No global shuffle, no difficulty sort. The only reordering anywhere is `sorted()` on shard
  **filenames** (batch order) in the loaders — never on content.

## Concrete numbers for `igsm_train_117M`

Generated with `--num-problems 117145600 --workers 200 --batch-size 131072`:

| Quantity | Value |
|---|---|
| Problems | 117.1M |
| Packed windows (768) | ~51M |
| Avg tokens/problem (derived) | ~334 |
| Shards (= batches) | ~894 |
| Chunks per shard (= workers) | 200 |
| Problems per chunk (`batch_size/workers`) | ~655 |
| **Same-difficulty chunk length** | **~285 windows** |
| Windows per shard | ~57,000 |

## Implication: shuffle is required; a modest buffer suffices *here*

Because same-difficulty chunks are ~285 windows long, training **without** shuffling would feed
near-homogeneous-difficulty batches that drift every few hundred steps — correlated gradients,
unstable optimization. So `src/train/gpt.py --stream` applies
`IterableDataset.shuffle(seed, buffer_size)`, which shuffles **both** shard order and a sample
buffer.

Buffer sizing depends on the **chunk length**, which depends on `workers`:

- **This dataset (200 workers, ~285-window chunks):** the default `--shuffle-buffer 10000` spans
  ~35 chunks → all op-levels present in the buffer at any moment → well-mixed batches. Sufficient.
- **Warning for future regenerations with few workers:** e.g. the README's `--workers 12`
  gives ~12× longer chunks (~2,800 windows). A 10k buffer would then hold only ~3–4 difficulties
  at a time. Rule of thumb: **`shuffle_buffer` ≳ windows-per-shard** (≈ one full batch) so every
  difficulty is represented. Many small workers → small chunks → easy mixing; few large workers →
  long chunks → needs a much bigger buffer (or accept difficulty-correlated batches).
